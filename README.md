# 智护忆站 —— 失智症家庭照护者压力监测与个性化支持系统

面向失智症家庭照护者的压力监测与支持系统原型：微信小程序（Taro + React）+ PocketBase 后端。

> 本项目是 EmoGuard（EMA 情绪记录小程序）方法学与业务逻辑的继承：同样以「即时评估（EMA）+ 分层干预 + 知识支持」为主线，
> 但后端从 Django + PostgreSQL + Redis + Celery 四件套换成 **PocketBase 单二进制 + SQLite**，
> 用约一个数量级的更少代码与运维面实现同等功能。

## 快速开始

### 1. 后端

```bash
cd carehaven
./pocketbase migrate up                 # 建表 + 灌初始数据
./pocketbase serve --http=127.0.0.1:8090
```

- 管理后台：`http://127.0.0.1:8090/_/`
- REST API：`http://127.0.0.1:8090/api/`

### 2. 前端

```bash
cd miniapp
bun install
bun run build:h5      # 网页版：产物在 miniapp/dist，可直接用浏览器验收
bun run build:weapp   # 微信小程序版：产物在 miniapp/dist，用开发者工具打开
```

H5 开发期可直接把产物拷进 `pb_public/` 由 PocketBase 托管（同源，无跨域问题）：

```bash
bun run deploy:h5    # 构建 H5 并同步到 ../pb_public（一条命令）
```

## 部署（Docker + GitHub Actions）

单容器：后端与 H5 产物打进同一个镜像，替换镜像标签即完成发布。

```
main 分支推送      → 自动构建镜像推送到 GHCR（不部署）
Actions 手动触发   → 自动部署：备份 → 切换 → 健康检查 → 失败自动回滚
```

- 镜像：`ghcr.io/<owner>/<repo>:sha-<8位>`，单架构 linux/amd64，层缓存走 Actions cache
- CI 相关文件：`Dockerfile`、`.dockerignore`、`docker-compose.yml`、`docker/{entrypoint,deploy,backup}.sh`、`.github/workflows/build-and-deploy.yml`
- 需要的仓库 Secrets：`SERVER_HOST`、`SERVER_USER`、`SERVER_SSH_KEY`
- 完整步骤、备份与回滚：见 **[docs/deploy-app-host.md](docs/deploy-app-host.md)**

⚠️ 不要起多副本：PocketBase 的定时任务是进程内的，多副本会重复执行。

## ⚠️ 数据来源声明（必读）

`physio_records` 中 `source = "simulated"` 的记录是**生理学约束下生成的合成数据**，用于验证系统链路，
**不是可穿戴设备真实采集的数据**。生理接入协议与数据通路（表结构、写入 API、`source` 字段）已设计并预留，
后续接入真实设备只需写入 `source = "device"` 的记录，前端与模型无需改动。

**任何汇报、论文、软著材料中涉及这些数据时，都必须如实标注为模拟/合成数据，不得描述为真实采集。**
这条关系到学术诚信，不可妥协。

## ⚠️ 合规与上线风险（重要）

当前代码为**内部原型**，仅在本机/内网运行，未对外开放注册与内容发布。上线前必须完成以下事项。
本节列举的风险中，**社群互助（发帖/评论）是合规门槛最高的一块**，也是能否上架的关键变量。

### 1. 用户生成内容（UGC）—— 最高风险

「社群互助」允许用户发布帖子和评论，属于 UGC 服务，触发以下义务：

- **平台内容审核责任**：《网络安全法》《网络信息内容生态治理规定》要求平台对用户发布内容承担管理责任，
  需具备**先审后发或机器审核 + 人工复核**能力、**举报入口**、**违规内容处置与留痕**机制。当前代码**没有**这些能力。
- **微信平台侧要求**：小程序开通社区/论坛类目通常需提供内容审核能力说明与相关资质；
  未取得资质而以其他类目上线 UGC 功能，存在被驳回或下架的风险。
- **处理建议**：短期演示保持「不开放注册 + 不对外开放」；若需上线，优先做的不是功能而是审核能力
  （关键字过滤 + 人工复核队列 + 举报入口 + 处置记录），或直接关闭匿名分区。

### 2. 小程序主体与类目资质

- 本项目属**健康管理**类目，**无需特殊资质**（不做诊疗、处方、医疗器械）；同类产品已有过审先例
  （EmoGuard 小程序 `wxfa9eb24a85ff200d`）。需要资质的是「医疗健康」下涉及诊疗类功能的类目。
- **UGC（社群/评论）是独立门槛**：社区/论坛类目需提供内容审核能力说明；个人主体无法开通该类目。
- 小程序请求域名必须 HTTPS 且加入微信后台白名单（域名 `care.example.com` 已就绪）；
- 类目与资质要求以微信官方最新规则为准，**上线前需逐项核对**（本文件不作为合规依据）。

### 3. 备案

- 服务器位于中国大陆时，域名需完成 ICP 备案；小程序需完成微信认证。

### 4. 个人信息与健康数据

- 本项目收集情绪、睡眠、照护负担等**属于敏感个人信息**的健康相关数据，
  依《个人信息保护法》需**单独同意**、遵循最小必要原则，并明确告知用途与保存期限；
- 敏感个人信息应境内存储；用户应能查询、导出、删除自己的数据（当前仅实现了删除的接口能力，未做界面入口）；
- 用于科研（论文/课题）时，还需通过**伦理审查**，并向参与者说明数据用途、匿名化处理方式。

### 5. 上线前检查清单

- [ ] 关闭或加固 UGC：审核能力、举报入口、违规处置留痕
- [ ] 小程序主体与类目资质核对完成
- [ ] 域名备案 + HTTPS + 微信后台白名单
- [ ] 隐私政策与单独同意流程（含敏感个人信息）
- [ ] 数据导出 / 删除入口
- [ ] 伦理审查与知情同意（若涉及真实用户与科研发表）
- [ ] 明确区分合成数据与真实数据，材料措辞复核

## 技术选型说明

| 维度 | 选择 | 理由 |
|---|---|---|
| 后端 | PocketBase | 单二进制含数据库/鉴权/权限规则/定时任务，运维面极小；表结构与权限用迁移文件表达 |
| 前端 | Taro 4 + React + TS | 一套代码编译出 H5 与微信小程序：H5 便于任何人用浏览器验收与截图，小程序用于正式交付 |
| 数据库 | SQLite（内嵌） | 单机、低并发场景足够；整个应用状态 = 一个数据目录，备份即拷贝 |
| 权限 | PocketBase API Rules | 数据归属规则直接表达在表定义上（如 `user = @request.auth.id`），无需在视图层重复判断 |

### 与 EmoGuard 的差异

| 项 | EmoGuard | 本项目 |
|---|---|---|
| 后端代码 | Django 约 6000 行（其中 63% 为框架样板） | 表结构 + 迁移 + 少量 hook |
| 组件 | Django + PostgreSQL + Redis + Celery + Nginx | 单二进制 |
| 权限 | 视图层逐处判断 | 表定义上的 API Rules |
| 定时推送 | Celery Beat + django-celery-beat | PocketBase cron |
