# 运营控制台：自带后台够不够

> 状态：结论已定（2026-11）。结论是**现在不建第二个控制台**，把缺的三个服务端能力补上即可。
> 能力项均以 PocketBase 0.40.5 实测接口为准（`/api/backups`、`/api/logs`、`/api/settings`、
> `/api/collections`，超管 token + 直接 PATCH 记录）。

## 1. 自带后台能做什么（已实测）

| 能力 | 入口 | 实测 |
|---|---|---|
| 记录增删改查 + 过滤 + 排序 | 集合列表 | `/api/collections/*/records` 超管读写 200 |
| 任意字段直接修改（含 `hidden`、`status`） | 记录编辑 | `PATCH whispers/{id} {"hidden":false}` → 200 |
| 表结构 / API 规则 / 索引编辑 | 集合设置 | 迁移与后台同一套 schema |
| 备份创建 / 下载 / 恢复 | Settings → Backups | `GET /api/backups` 200 |
| 请求日志与错误日志 | Logs | `GET /api/logs` 200，含 `level`/`message`/`data` |
| 速率限制、代理、SMTP、S3 | Settings | `settings.rateLimits/logs/backups/smtp/s3/trustedProxy/superuserIPs` |
| 超管管理、IP 白名单 | Settings | `superuserIPs` 字段存在 |

**关键结论**：举报处置、隐藏/恢复、反馈状态流转、用户停用，这些都能在自带后台完成，不需要新界面。

## 2. 运营任务 × 覆盖情况

| 任务 | 频率（pilot 期） | 自带后台 | 缺口 |
|---|---|---|---|
| 处理被举报的 `whispers` | 每周个位数 | 过滤 `report_count > 0 || hidden = true`，改 `hidden` / 删除 | **无处置留痕** |
| 反馈 triage | 每周几条 | 改 `feedback.status` | 无提醒、无 SLA |
| 用户停用/删除 | 偶发 | 编辑/删除 users（级联删除其记录） | 无导出/注销流程 |
| 改 HPS 权重与阈值 | 极低频 | 改 `app_config.value` | **无校验、无历史** |
| 查问题 | 随时 | `/api/logs` + 容器日志 | 无告警外发 |
| 备份恢复 | 月度演练 | 后台一键恢复 | 未演练 |
| 词库调整 | 每次发版 | —（代码） | 有意为之 |
| 研究导出 | 每个研究批次 | — | **完全没有** |

## 3. 结论

**不建独立控制台。** 理由不是"够用"，而是三条：

1. **缺的不是界面。** 上面 8 个任务里，只有 3 个是"后台点不了"的：处置留痕、配置历史/校验、数据导出。这三个都是**服务端能力**，补完之后自带后台就能操作。
2. **第二套 UI 会带来第二套约定。** 认证、权限、脱敏、审计、告警、部署全要重做；单人运营的项目没有收益。
3. **风险重心在审计而不是效率。** 真正会被问到的是"谁在什么时候隐藏了哪条、为什么"，而不是"操作快不快"。

## 4. 要补的三个服务端能力（仍用自带后台操作）

| # | 能力 | 状态 | 实现 |
|---|---|---|---|
| C1 | 处置留痕 | ✅ 2026-11 | `POST /api/zz/moderation/whispers/{id}`（超管，必须给理由）→ 写 `moderation_actions`（actor / action / reason / before / after）。PID 重置幂等：状态未变不重复记录 |
| C2 | 配置治理 | ✅ 2026-11 | `app_config` 写入校验（Σw=1、0≤w≤1、阈值有序、区间 lo<hi）+ `app_config_history`；非法值 400 |
| C3 | 数据权利 | ✅ 2026-11 | 导出/注销接口 + 「我的 - 我的数据」入口；`research_consents` 记录同意与撤回，数据集按同意过滤 |

处置走接口而不是后台手改字段：手改没有理由、也没有可举证的记录。后台仍可用于查询与只读排查。

这三项与 [platform.md](platform.md) 的 A4 / A6 / B2 是同一件事，在那边有依赖与排期，这里只标运营视角。

## 5. 什么时候必须自建控制台

出现任意两条，就该立项：

- 运营从 1 人变 3 人以上，需要角色分离（审核 / 研究 / 运维）与最小权限；
- 外部要求提供**处置报告**（时间、操作者、依据），后台改字段已经无法举证；
- 每日需要看面板（新增、活跃、依从率、举报量、TTS 支出），靠人翻集合不可行；
- 研究导出变成周频，需要固定视图、字段脱敏与同意状态联动；
- 需要"只读观察者"账号（导师、合作者）而不想给超管。

自建时的最小形态：**只读运营页**（指标 + 举报队列 + 导出触发），写操作仍回自带后台或专用路由，避免出现第二个可写入口。
