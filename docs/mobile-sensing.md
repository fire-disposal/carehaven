# 手机端数据采集：Flutter 是否划算

> 状态：分析（2026-11）。结论：**在"不做硬件"的前提下，Flutter 伴侣应用是可行但只在特定边缘条件下划算。**
> 更便宜的第一步是「健康数据导入 + 小程序 BLE」，Flutter 应作为第二阶段。

## 1. 结论

| 方案 | 开发成本 | 年度运维 | 能拿到的数据 | 何时选 |
|---|---|---|---|---|
| A. 保持小程序 + 手动录入 | 0 | 低 | 自评、手动生理、结构化互助 | 默认；以量表为主线 |
| B. 小程序 + 标准 BLE 设备 | 3–5 人日 | 低 | 心率/HRV/步数（用时要开着小程序） | 想做设备验证、n<30 |
| C. 健康数据导入（HealthKit / Health Connect 导出） | 2–4 人日 | 低 | 步数、睡眠、心率、体重等**历史**数据 | 用户已有手表，可接受周级延迟 |
| D. **Flutter 伴侣应用** | **3–6 周**（单人） | $99/年 + 备案 + 每次审核 | 后台同步、步数/睡眠/HR/HRV、BLE、通知 | 被动数据是**主要结局**，且研究 ≥3 个月 |
| E. 自研可穿戴 | 6 个月+，硬件认证 | 高 | 与设备强绑定 | 不推荐（预算不允许） |

判断规则：**如果主要结局仍是 ZBI/PHQ/GAD 自评，手机被动数据只是协变量 → 不做 D**；
如果研究要回答"生理/睡眠变化能否提前预警"，D 才成立。

## 2. 手机实际能给什么（没有自研硬件）

| 指标 | 来源 | 现实约束 |
|---|---|---|
| 步数、活动能耗 | HealthKit / Health Connect | 需要用户授权；Android 碎片化 |
| 睡眠时长/分期 | 手机算法或已连接的手表 | 精度差异大，必须带设备型号 |
| 心率 | 手表同步，或手机摄像头 PPG | 摄像头 PPG 的 HRV 不可用于研究结论 |
| HRV | 仅手表/指环记录 | 用户是否戴表决定样本选择性 |
| GSR/EDA | **手机拿不到** | HPS 的生理分含 GSR，必须改为缺失语义或重新赋权 |
| 位置/停留 | 系统定位 | 隐私敏感、耗电、审核风险 |
| 通知与提醒 | 原生推送 | 小程序订阅消息受限，原生应用显著改善依从 |

关键结论：**手机能补"活动/睡眠/心率"，补不了"皮电"。** 而当前 HPS 的生理分是 HRV、GSR、睡眠三项等权平均——没有 GSR 时，`coverage` 会长期缺一项，需要重新定义分量或明确"设备子研究"。

## 3. 成本拆解（估算，非报价）

| 项 | Flutter 伴侣应用 | 说明 |
|---|---|---|
| 开发 | 3–6 周 × 1 人 | 登录/同意/研究码、健康数据同步、BLE、打卡、结果页；复用现有 REST |
| 联调与后端 | 1 周 | 需要 `/api/zz/physio/device` 与 `device_registry`（当前未实现） |
| 合规 | 1–3 周等待 | App 备案、隐私清单、健康数据权限说明；iOS 审核对健康类更严 |
| 运维 | 1–2 天/月 | 双端构建、SDK 升级、商店政策变化 |
| 现金 | Apple $99/年 | Android 国内商店多需软著/备案材料 |

对照：小程序路径**没有**额外商店成本，但也**拿不到** HealthKit/Health Connect。

## 4. 技术选型：Flutter 还是 React Native

- 团队已有 React/TypeScript 经验（Taro），后端类型可复用 → **React Native 的学习成本更低**；
- Flutter 的优势是双端 UI 一致、插件生态成熟（`health`、`flutter_blue_plus`）；
- 若团队只有一个人且要长期维护，选**自己更熟的那一个**比框架优劣重要。
- 两者都需要原生权限声明；都能读 HealthKit/Health Connect；后台采集都受系统限制（iOS BGTaskScheduler、Android 前台服务）。

**结论**：从"成本/收益"看，Flutter 与 React Native 差距不大；若严格按现有技能栈，React Native 更便宜。

## 5. 与本系统的对接方式

```mermaid
flowchart LR
  APP[Flutter/RN 伴侣应用] -->|OAuth token| API[/api/zz/*]
  API --> Q[服务端写入校验]
  Q --> P[(physio_records<br/>source=device)]
  Q --> D[(device_registry<br/>device_tokens)]
  P --> H[HPS 计算<br/>coverage 标注缺失]
  H --> E[(stress_score_events)]
```

需要补的服务端能力（与 [backend-roadmap](backend-roadmap.md) P0 一致）：

1. `device_registry` / `device_tokens`：设备注册、轮换、吊销；
2. `POST /api/zz/physio/device`：token 鉴权、幂等（按设备 + 时间窗去重）、服务端写 `received_at`；
3. `physio_records` 增加 `device_model`、`firmware`、`sampling`、`quality`；
4. 聚合策略：原始样本保留（研究用），日级汇总进 `physio_records`（HPS 用）；
5. 缺失语义：某指标整天缺失 → `coverage=false`，不写 0。

## 6. 测量学影响（必须提前写进方案）

- **设备异质性**：不同手表/算法测出的睡眠分期不可直接平均；分析时设备作为随机效应或分层变量。
- **选择性偏倚**：愿意戴表的人可能更年轻、更配合 → 报告设备持有率与佩戴依从。
- **缺失机制**：佩戴缺失通常非随机（出差、生病），必须报告并按分量覆盖率分析，不做零填充。
- **测量不变性**：跨设备比较前先做一致性检验（Bland–Altman），不通过就不合并。
- **皮电缺失**：要么把生理分改为"HRV + 睡眠"两项并升版算法（`hps-3`），要么在研究中把生理分标为部分覆盖。

## 7. 分阶段建议

| 阶段 | 动作 | 成本 | 产出 |
|---|---|---|---|
| 0 | 研究方案写明"被动数据是否为主要结局" | 0 | 决策依据 |
| 1 | 小程序 + 标准 BLE 手环读取心率/HRV（前台） | 3–5 人日 | 设备链路可行性、佩戴依从 |
| 2 | 健康数据导入（用户从 Apple Health/Health Connect 导出后上传） | 2–4 人日 | 历史步数/睡眠，周级延迟 |
| 3 | Flutter/RN 伴侣应用（仅在 1–2 证明有增量价值后） | 3–6 周 | 被动数据 + 通知依从 |
| 4 | 自研硬件 | 不推荐 | — |

**止损条件**：若 1–2 阶段显示"用户不愿佩戴/不愿授权"，或被动数据与研究结局相关性接近 0，则不做第 3 阶段。

## 8. 没有 iOS 设备时的平台矩阵

结论先说：**现在不做 iOS 原生；iPhone 用户继续用小程序/H5。** iOS 构建的硬门槛不是框架，而是 macOS + Xcode（或云 Mac），以及没有设备时的验证手段。

| 客户端 | 覆盖用户 | 能拿到的数据 | 无 iOS 设备时可否开发 | 无 iOS 设备时可否验证 |
|---|---|---|---|---|
| 微信小程序（现有 Taro） | iOS + Android（微信内） | 自评、手动、前台 BLE | 可以 | 可以（开发者工具 + 真机 Android） |
| H5 | 全平台浏览器 | 同上，无后台/BLE | 可以 | 可以（Chromium/Safari 桌面） |
| Android 原生（Kotlin） | Android | Health Connect、后台、BLE | 可以 | 可以（模拟器 + 真机） |
| Flutter | Android | 同 Kotlin | 可以 | Android 充分；**iOS 无法验证** |
| Flutter/RN iOS 构建 | iOS | 同 Android | 需要 macOS 或 CI macOS runner | 模拟器（需 Mac）/云真机（付费）/TestFlight（需 iPhone 测试者） |

现实约束：

- 私有仓库用 GitHub Actions 的 `macos-latest` 按 10 倍分钟计费；一次 iOS 构建 + 归档约 10–20 分钟，长期不便宜。
- Flutter 的 iOS 侧问题（权限弹窗、HealthKit 授权、后台刷新）**只有真机能确认**；模拟器不能覆盖健康数据与 BLE。
- 云真机（BrowserStack / Sauce Labs）按分钟付费，适合发布前冒烟，不适合日常迭代。

因此建议的**受支持矩阵**（写进研究方案与 README）：

| 平台 | 支持级别 | 说明 |
|---|---|---|
| 微信小程序 | 一级 | 全部核心功能（自评、问答、互助、减压、研究入组） |
| Android 伴侣应用（可选） | 二级 | 被动数据采集；仅在"被动数据是主要结局"时开发 |
| iOS 原生/伴侣应用 | 暂不支持 | iPhone 用户走小程序；方案里声明该限制 |
| H5 | 三级 | 只作分享与兜底，不承诺后台能力 |

## 9. 非目标

- 不用手机摄像头 PPG 做 HRV 研究结论；
- 不把不同设备的睡眠分期合并成一个变量；
- 不为了"有设备数据"而降低研究方案的可解释性；
- 不在没有设备鉴权与幂等的情况下开放设备写入。
